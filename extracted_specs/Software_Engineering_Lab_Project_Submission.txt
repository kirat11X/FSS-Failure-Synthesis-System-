1. Introduction 
1.1 Purpose 
 
The Failure Synthesis System is designed to preserve, retrieve, and reconstruct 
historical event information generated by distributed autonomous systems such as 
drone fleets, robotic systems, or other cooperating services. 
The system addresses two major challenges: 
1.​ Reliable preservation of event evidence when the central event-processing system 
unexpectedly crashes. 
2.​ Reconstruction of relevant historical context when the cause of a failure may 
involve events generated by multiple sources. 
After relevant evidence has been reconstructed, an AI reasoning layer interprets the 
available information and produces a failure explanation while explicitly identifying 
information that cannot be determined. 
This document specifies the functional and non-functional requirements of the 
system. 
1.2 Scope 
The system receives structured events from multiple event-producing sources and 
records them in a central persistent storage system. 
An event may represent information such as: 
●​ Position or state updates 
●​ Sensor states 
●​ Planner or controller transitions 
●​ Warnings 
●​ Faults 
●​ Internal system events 
The system provides: 
●​ Concurrent event ingestion 
●​ Crash-tolerant persistent storage 
●​ Historical event retrieval using bounded time ranges 
●​ Retrieval across one or multiple sources 
●​ Event-type filtering 
●​ Recovery of persisted data after an unexpected shutdown 
●​ Deterministic interpretation of structured event payloads 
●​ Cross-source context reconstruction 
●​ AI-assisted failure synthesis 


--- [Page 5] ---
The project does not assume that every event or payload can be completely 
interpreted. Unknown information is preserved and reported as unknown rather than being 
inferred without supporting evidence. 
1.3 Problem Statement 
In a fleet of autonomous drones, the cause of a failure may not originate from the 
source that exhibits the visible failure. 
For example, suppose Drone 474 unexpectedly leaves its formation. Another drone, 
such as Drone 298, may have previously experienced a sensor failure that changed its 
behavior. Drone 474 may then have reacted through its avoidance or planning system. 
Therefore, retrieving only the events generated by Drone 474 may not provide 
sufficient evidence to reconstruct the failure. 
At the same time, the central event-processing system may itself terminate 
unexpectedly. Events that have already been received but remain only in memory, or records 
that are partially persisted during the crash, may be lost or corrupted. 
The system therefore needs to provide both reliable event preservation and efficient 
historical context reconstruction. 
1.4 Objectives 
The main objectives are: 
●​ To accept events from multiple independent sources. 
●​ To persist received events in crash-tolerant storage. 
●​ To recover valid previously persisted information after an unexpected shutdown. 
●​ To retrieve historical events using bounded time ranges. 
●​ To support retrieval across multiple sources when the relevant cause is distributed. 
●​ To preserve raw event information even when its payload cannot be interpreted. 
●​ To decode event payloads deterministically using configured schemas and domain 
knowledge. 
●​ To reconstruct relevant cross-source context. 
●​ To use an AI reasoning layer to synthesize an explanation from reconstructed 
evidence. 
●​ To distinguish known information from information that remains unknown.

2. Overall Description 
2.1 Product Perspective 
The system acts as a central event recording and failure reconstruction platform. 
A high-level view is: 
 


--- [Page 7] ---
The core event system is implemented in Java. The intelligence layer responsible for 
deterministic payload interpretation, domain knowledge/RAG, AI reasoning, and final 
presentation is implemented in Python. 
2.2 System Users and External Entities 
Event Producers 
Autonomous drones, robots, services, or other distributed sources that continuously 
generate events and send them to the central system. 
Investigator 
A user who requests historical information about a failure and receives reconstructed 
evidence and an AI-generated synthesis. 
Domain Knowledge / Schema Source 
Provides the configuration and domain information required to interpret structured 
event payloads. 
AI Reasoning Layer 
Consumes reconstructed and interpreted evidence and generates the final failure 
synthesis. 
2.3 Major System Components 
The system consists of the following major components: 
1.​ Event Ingestion 
2.​ Event Validation and Envelope Parsing 
3.​ Persistent Storage 
4.​ Block Allocation and Management 
5.​ Crash Recovery 
6.​ Historical Retrieval 
7.​ Event Decoding 
8.​ Context Reconstruction 
9.​ AI Failure Synthesis 
10.​Result Presentation

3. Functional Requirements 
FR-01 — Event Ingestion 
The system shall accept structured events generated by multiple independent event 
sources. 
Each received event shall contain sufficient information for the system to identify its 
source, timestamp, event type, payload length, and payload. 
FR-02 — Concurrent Event Handling 
The system shall support concurrent connections from multiple event producers. 
The ingestion subsystem shall decouple incoming event reception from persistent 
storage so that events can be processed by the storage subsystem without requiring each 
producer connection to directly perform storage operations. 
FR-03 — Event Validation 
The system shall validate the structural information required to process an incoming 
event. 
Invalid or incomplete event envelopes shall not be treated as valid persisted events. 
FR-04 — Persistent Event Storage 
The system shall persist received events to non-volatile storage. 
Events shall be stored in fixed-size storage blocks. 
An event shall not cross a block boundary. 
If an event cannot fit in the remaining space of the current block, the unused space 
shall remain unused and the event shall be written to another block. 
FR-05 — Event Record Preservation 
The system shall preserve the following information for each event: 
●​ Source identifier 
●​ Timestamp 
●​ Event type 
●​ Payload length 
●​ Payload bytes 
The payload shall be preserved even when its semantic meaning is not known to the 
system. 
FR-06 — Block Metadata Management 
The system shall maintain metadata required to locate and validate persisted blocks. 
Block metadata shall include: 
●​ Block identifier 


--- [Page 9] ---
●​ Storage offset 
●​ Used length 
●​ Start timestamp 
●​ End timestamp 
Logical time-based segments shall maintain mappings between event sources and the 
blocks containing their events. 
FR-07 — Crash Recovery 
The system shall recover persisted event information after an unexpected 
central-system shutdown. 
During recovery, the system shall identify incomplete or corrupt trailing event data in 
an active block and ensure that such incomplete data is not treated as a valid event. 
Previously completed valid events shall remain available for retrieval. 
FR-08 — Historical Retrieval 
The system shall support retrieval of historical events using a bounded time interval. 
The retrieval operation shall support: 
●​ A specific source and time range 
●​ All sources within a time range 
●​ Optional event-type filtering 
The system shall not require unrestricted historical retrieval without a time boundary. 
FR-09 — Cross-Source Retrieval 
The system shall support retrieval of events belonging to multiple sources within the 
requested time interval. 
This allows the system to reconstruct failures whose relevant events originated from 
sources other than the source exhibiting the failure. 
FR-10 — Event Decoding 
The system shall decode event payloads according to configured schemas and domain 
knowledge. 
Payload interpretation shall be deterministic wherever a corresponding schema or 
domain definition is available. 
Payload fields whose meaning is not defined by available knowledge shall remain 
explicitly unknown. 
FR-11 — Context Reconstruction 
The system shall combine retrieved events from relevant sources and time intervals to 
construct historical failure context. 
The reconstruction process shall preserve the temporal and source information 
associated with the events. 


--- [Page 10] ---
FR-12 — AI Failure Synthesis 
The system shall provide reconstructed evidence to the AI reasoning layer. 
The AI layer shall synthesize a failure explanation based on the available evidence 
and supplied domain knowledge. 
The generated explanation shall distinguish supported information from information 
that cannot be determined from the available evidence. 
FR-13 — Failure Investigation Result 
The system shall provide the investigator with: 
●​ Relevant historical events 
●​ Reconstructed context 
●​ Interpreted event information 
●​ The synthesized failure explanation 
●​ Explicit indication of unknown or uninterpretable information 
 
4. Non-Functional Requirements 
NFR-01 — Durability 
Events that have been successfully persisted shall remain recoverable after an 
unexpected termination of the central event-processing system. 
NFR-02 — Crash Consistency 
The storage subsystem shall prevent incomplete event records from being interpreted 
as valid records after recovery. 
NFR-03 — Performance 
The system shall support efficient ingestion and retrieval without requiring the 
complete historical event dataset to be loaded into memory. 
NFR-04 — Bounded Retrieval 
Historical queries shall operate over explicitly specified time ranges to prevent 
uncontrolled retrieval of the entire event history. 
NFR-05 — Concurrency 
The ingestion subsystem shall support multiple concurrent event producers. 
NFR-06 — Scalability 
The architecture shall allow the number of event-producing sources and stored events 
to grow without requiring the complete historical dataset to remain in memory. 


--- [Page 11] ---
Large-scale deployment capacity shall be evaluated through implementation 
benchmarks rather than assumed as a fixed performance guarantee. 
NFR-07 — Reliability 
The system shall continue to provide access to valid previously persisted evidence 
after recovery from an unexpected central-system failure. 
NFR-08 — Extensibility 
The event format and payload interpretation mechanism shall allow different 
deployments to use different configured event envelopes and payload schemas. 
NFR-09 — Interpretability 
The AI reasoning layer shall not be required to infer the meaning of unexplained raw 
payload fields. 
Unknown or unsupported information shall be explicitly identified. 
NFR-10 — Separation of Responsibilities 
The system shall maintain a separation between: 
●​ Event ingestion and persistence 
●​ Historical retrieval 
●​ Deterministic payload interpretation 
●​ Context reconstruction 
●​ AI reasoning

5.2 Block Metadata 
Each physical storage block shall maintain: 
Field 
Description 
Block ID 
Unique identifier of the block 
Storage Offset Position of the block in persistent storage 
Used Length 
Number of valid bytes currently stored 
Start Time 
Timestamp of the first event in the block 
End Time 
Timestamp of the last event in the block 
5.3 Logical Segment Information 
Segments represent logical time-based groupings of stored data. 
A segment maintains associations between event sources and the block identifiers 
containing their events. 
Segments are logical storage metadata and are not required to correspond to 
individual physical files. 
 
6. System Architecture 
6.1 Java Core 
The Java subsystem is responsible for: 
●​ Network/event ingestion 
●​ Envelope parsing 
●​ Event validation 
●​ Buffer management 
●​ Persistent storage 
●​ Block allocation 
●​ Block metadata 
●​ Crash recovery 
●​ Historical retrieval 
The primary storage implementation uses positional file I/O through FileChannel with 
ByteBuffer for binary data handling. 


--- [Page 13] ---
6.2 Python Intelligence Layer 
The Python subsystem is responsible for: 
●​ Deterministic payload decoding 
●​ Schema/domain-knowledge integration 
●​ Retrieval context processing 
●​ RAG/domain knowledge processing where applicable 
●​ AI-based failure synthesis 
●​ Presentation of the reconstructed failure context 
6.3 Data Exchange 
The Java core shall provide retrieved events to the intelligence layer in a structured 
representation equivalent to: 
EventRecord 
    source_id 
    timestamp 
    event_type 
    payload_bytes 
 
The intelligence layer shall use this information to decode and interpret the retrieved 
evidence. 
 
7. Constraints and Assumptions 
7.1 Constraints 
●​ The central system is responsible for persistent event storage. 
●​ Events are assumed to be received by the central system before they can be persisted. 
●​ The system does not assume synchronized clocks across all event sources. 
●​ Events shall not span physical storage blocks. 
●​ Historical retrieval requires a bounded time interval. 
●​ Raw payload interpretation depends on configured schemas or domain knowledge. 
●​ The AI layer shall not treat unknown payload fields as known facts. 
7.2 Assumptions 
●​ Event producers can communicate with the central event-processing system. 
●​ Events follow a configured binary envelope format for a given deployment. 
●​ The envelope layout may be configured for different deployments. 
●​ Persistent storage is available to the central system. 


--- [Page 14] ---
●​ Domain knowledge required for interpreting supported payloads is available to the 
intelligence layer. 
●​ The system is intended to preserve evidence generated before a central-system crash; 
fault tolerance of the individual drones themselves is outside the primary scope.  
 
8. Expected System Outcome 
The completed system shall provide a reliable historical evidence layer for 
investigating failures in distributed autonomous systems. 
 
For a failure such as an unexpected deviation by Drone 474, the system should be 
capable of retrieving relevant events from the requested time interval, including events 
produced by other sources such as Drone 298, reconstructing the available context, and 
producing an AI-assisted explanation based only on the evidence that can be supported by the 
available data. 
The system shall preserve unknown or uninterpretable information rather than presenting 
unsupported assumptions as facts.
