Hardening the Java–Python Integration Bridge

Because your Java core is complete and verified against zero core mutations, the integration boundary (bridge/java_retriever.py and the Java CLI or worker wrapper invoking BlockStore) carries the highest concentration of OS-level failure modes. Five concrete hazards merit immediate attention.

Subprocess Deadlocks, the 64KB Pipe Wall, and Orphan Process Cleanup

When Python spawns a JVM through subprocess.Popen(..., stdout=PIPE, stderr=PIPE)—or when Java invokes child commands through ProcessBuilder—the Linux kernel creates separate in-memory pipe buffers for STDOUT (FD 1) and STDERR (FD 2), each capped at approximately 64KB on modern Linux systems. Because your BlockStore persists data in 64KB blocks, even a single verbose telemetry response, block dump, or Java stack trace alongside JSON metadata can fill a pipe buffer completely. Once full, the kernel suspends the writing child mid-execution until the parent reads from the pipe; if the parent calls Popen.wait() in Python or Process.waitFor() in Java before draining both pipes concurrently, both processes deadlock indefinitely without raising an exception or stack trace.

Official Python subprocess documentation highlights four additional lifecycle bugs that directly threaten bridge/java_retriever.py inside a multithreaded Streamlit server. First, when proc.communicate(timeout=...) raises TimeoutExpired, Python does not automatically kill the child process; the caller must terminate the child and invoke a second proc.communicate() (with no input) to drain remaining pipe data and reap the process exit status, and must never call proc.wait() after a timeout (as full pipe buffers can also block wait() in asynchronous subprocess wrappers even after a termination signal). Second, passing preexec_fn (such as preexec_fn=os.setsid) is explicitly documented as not safe in multithreaded applications—and Streamlit runs concurrent server, script, and worker threads—because it can deadlock the child before exec. Replace any preexec_fn calls with start_new_session=True (POSIX, Python 3.2+) or process_group=0 (Python 3.11+) so timeout handlers can cleanly signal the entire child process group (SIGTERM, brief grace wait, then SIGKILL) and prevent orphaned grandchildren.

Third, enabling text=True (or universal_newlines=True) without specifying encoding falls back to locale.getpreferredencoding(False), creating silent Unicode decode failures across differing container or shell locales. Always read raw binary streams (text=False) and decode explicitly as strict UTF-8 (matching RFC 8259 §8.1's UTF-8 mandate for JSON interchange), paired with -Dfile.encoding=UTF-8 on the JVM invocation. Fourth, because communicate() buffers the entire child output in memory, enforce a strict byte ceiling on bounded retrieval responses, resolve the java executable explicitly via shutil.which("java") (or $JAVA_HOME/bin/java) rather than shell=True, wrap all Java process streams in try-with-resources to prevent file-descriptor leakage against ulimit -n caps, and traverse Java 9+ ProcessHandle.descendants() if Java itself spawns helper subprocesses.

Replacing Stdout Scraping with Framed Wire Protocols and Persistent IPC

Commit 4a4f568 hardened JSON metadata extraction from JVM stdout streams, mitigating immediate crashes from noisy startup lines. Still, scraping raw stdout remains fragile in production environments: setting JAVA_TOOL_OPTIONS or _JAVA_OPTIONS causes many OpenJDK builds (prior to the banner removal introduced in Oracle JDK 8u351+) to print Picked up JAVA_TOOL_OPTIONS: ..., and any merged stderr line or stray System.out.println from a dependency immediately breaks unframed stream parsers.

To harden the wire channel today, keep stderr strictly separated from stdout (never pass stderr=subprocess.STDOUT or Java redirectErrorStream(true) on a machine-readable JSON pipe). Inside the Java wrapper's main(), capture the raw protocol stream on FileDescriptor.out first and reassign System.setOut to System.err so accidental prints can never corrupt the data channel. Over that clean channel, adopt one of two standard framings:

NDJSON (Newline-Delimited JSON): Emit one compact, UTF-8 JSON object per line with no embedded newlines, terminated by \n—the exact stdio transport standardized across the Model Context Protocol (MCP) Python, TypeScript, Go, and C# SDKs.

LSP-Style Content-Length Byte Framing: Emit an ASCII header (Content-Length: <byte_count>\r\n\r\n) followed by exact UTF-8 JSON-RPC 2.0 bytes. If using this format, count UTF-8 bytes rather than character length (mixing them truncates multi-byte telemetry) and cap maximum accepted frame length to prevent memory exhaustion on corrupt headers. Never mix NDJSON and Content-Length framing across client and server, as mismatched framing causes indefinite handshake timeouts.

Beyond wire framing, spawning a fresh JVM on every Streamlit interaction pays repeated classloading and initialization overhead while discarding JIT compilation. Measured JVM startup costs range from ~62 ms for a minimal ~450-class HelloWorld on an M4 MacBook Pro (with verbose trace logging) and 31 ms for HelloStream on JDK 23 (falling 42% to 18 ms with JDK 24 AOT Cache under JEP 483), up to 497–939 ms for a JSON-serving Quarkus sample application in Red Hat's OpenJDK 17 benchmarks (939 ms with -Xshare:off, 869 ms with JDK CDS, and 497 ms with AppCDS + JDK CDS). End-to-End Unsigned 64-Bit Timestamp Integrity From findMinTs to Browser UI

Commit 4a4f568 corrected unsigned 64-bit integer comparisons in findMinTs() (analogous to Long.compareUnsigned), yet fixing Java-side comparison protects only one third of the data path. Two silent corruption bugs persist downstream unless addressed across the wire contract and UI. First, because Java's long primitive is strictly signed (-2^63 to 2^63 - 1), any default JSON numeric serializer or String.valueOf(ts) emits unsigned values ≥ 2^63 as negative integers (2^63 serializes as -9223372036854775808, and 2^64 - 1 serializes as -1). Java must encode all unsigned 64-bit timestamps with Long.toUnsignedString(ts) and parse them with Long.parseUnsignedLong(str).

Second, RFC 8259 Section 6 explicitly warns that JSON numeric literals are only guaranteed interoperable without precision loss inside the IEEE 754 binary64 safe integer range [-(2^53) + 1, (2^53) - 1] (or ±9,007,199,254,740,991). While Python parses arbitrary-precision integers losslessly, Streamlit transmits dataframes (st.dataframe), charts, and JSON views (st.json) into browser JavaScript—where Pandas/NumPy int64 columns can trigger JSON serialization TypeErrors and raw uint64 values silently lose precision beyond 53 bits. Concurrency Safety and File Locking on 64KB BlockStore Files

Because streamlit_app.py now persists directly into Java BlockStore 64KB blocks while serving bounded retrievals, concurrent browser sessions—or rapid user clicks under Streamlit's default runner.fastReruns = true—can issue overlapping writes and reads against the same storage files. Three Linux and JVM locking semantics create dangerous corruption traps if mixed improperly. First, since Linux 2.0, BSD flock(2) locks (Python fcntl.flock) and POSIX fcntl(2) record locks (F_SETLK / Java FileChannel.lock()) use completely separate kernel tables that do not interact on local filesystems. If Python acquires flock while Java acquires FileChannel.lock(), neither process blocks the other, permitting interleaved torn writes inside a 64KB block.

Second, Java NIO file locks are held on behalf of the entire JVM, not individual threads. Once you migrate to a persistent multi-threaded Java worker, two threads locking overlapping byte regions of the same BlockStore file will trigger an unchecked OverlappingFileLockException. Third, traditional POSIX fcntl record locks carry a notorious descriptor trap: closing any file descriptor referring to the same file within a process drops all POSIX locks held by that process on that file. (Linux 3.15+ introduced F_OFD_SETLK open-file-description locks to resolve this per-FD issue, and both lock families behave inconsistently across NFS and SMB mounts.)

The cleanest remediation is a strict single-writer ownership invariant: Python must never open BlockStore data files for writing. Inside Java, guard every BlockStore write first with an in-JVM ReentrantReadWriteLock (serializing threads cleanly without OverlappingFileLockException) and then with FileChannel.lock() inside a try-with-resources block, calling fileChannel.force(true) to flush data and metadata before releasing the lock. While running one-shot Python-to-Java CLI spawns during Phase 1, wrap write-capable JavaRetriever calls on the Python side with both a global threading.Lock (cached via @st.cache_resource) and an exclusive lock on a separate sidecar .lock file using fcntl.lockf (which wraps POSIX fcntl record locking on Linux).

Eliminating sitecustomize.py and Fixing Streamlit Lifecycle and Concurrency Bugs

Commit 4a4f568 introduced a repo-root sitecustomize.py for Python path configuration and delegated app.py to streamlit_app.py. Official Python and Streamlit documentation highlights four brittle failure modes across these files that should be refactored immediately.

First, replace sitecustomize.py with an editable package (pyproject.toml). Local LLM Inference Hardening: Context Budgeting, Qwen3 Decoding Stability, and Constrained Output

Running an 8-part Root Cause Synthesis prompt locally exposes two quiet failure modes that yield fluent yet invalid diagnoses: silent prompt truncation in Ollama and decoding loops in Qwen3 models. Current Ollama releases choose a default context window (num_ctx) dynamically from detected GPU VRAM: 4,096 tokens under 24 GiB VRAM, 32,768 tokens for 24–48 GiB, and 262,144 tokens for 48 GiB or more (older builds defaulted to 2,048). Crucially, when an FSS prompt overflows num_ctx, Ollama returns HTTP 200 and silently truncates the oldest tokens—dropping system instructions, epistemic rules, or early causal telemetry without emitting a warning—whereas llama.cpp (llama-server) fails fast with HTTP 400 exceed_context_size_error.

To quantify this headroom risk for your 8-part synthesis prompt, an illustrative token-budget model (assuming 850 tokens for system/schema instructions, 1,200 tokens for top-5 Domain RAG chunks, 300 tokens for Data Gaps and question framing, 45 tokens per structured timeline event, and 1,200 non-thinking vs. 3,200 thinking output tokens) shows why 4,096 tokens breaks immediately.

In addition to sizing num_ctx ≥ 16384 (and verifying with a Python pre-flight token budget guard before every call), watch out for two documented Ollama configuration traps. First, OLLAMA_NUM_CTX is not a real Ollama setting—direct testing on Ollama 0.34.1 confirmed that the server ignores unrecognized environment variables silently; the real server variable is OLLAMA_CONTEXT_LENGTH=16384, which on systemd Linux services must be configured via sudo systemctl edit ollama rather than an interactive shell export. Second, Ollama's OpenAI-compatible /v1/chat/completions endpoint silently drops num_ctx from request JSON payloads (openai/openai.go has no field for it); you must configure context via OLLAMA_CONTEXT_LENGTH, a custom Modelfile (PARAMETER num_ctx 16384), or Ollama's native /api/chat (options.num_ctx), and avoid oscillating num_ctx between requests because changing it forces a multi-second model reload. Always inspect the live effective window in the CONTEXT column of ollama ps.

If your synthesis layer runs Qwen3 (or upgrades from Qwen2.5), four inference controls eliminate repeating-token hangs and malformed outputs. First, never use greedy decoding (do_sample=False / temperature=0) when Qwen3 Thinking Mode (enable_thinking=True) is active: official Qwen3 documentation warns that greedy decoding in thinking mode causes performance degradation and endless repetition loops, and independent testing on Qwen3.5 (0.8B/2B/4B) reproduced infinite unclosed <think> loops even under pinned llama.cpp. Use Qwen3's documented sampling defaults (temperature=0.6, top_p=0.95, top_k=20, min_p=0, with optional presence_penalty up to 1.5–2.0 if loops persist) for thinking mode, or disable thinking via the hard switch (enable_thinking=False) with temperature=0.7, top_p=0.8, top_k=20, min_p=0 for lower-latency structured synthesis. Second, implement Qwen's official bounded think-budget guard: parse closing thinking token ID 151668 (</think>) and end-of-message token ID 151645 (<|im_end|>); if Phase 1 decoding hits thinking_budget (recommended > 1,024 tokens in production) without emitting 151668, append the early-stopping string "\n\nConsidering the limited time by the user, I have to give the solution based on the thinking directly now.\n</think>\n\n", surface an explicit reasoning_truncated: true status in the UI rather than failing silently, and decode the final answer within the remaining token budget.

Third, guard against HuggingFace transformers GenerationConfig edge cases: passing do_sample=False alongside temperature=0.0 triggers UserWarning or division-by-zero ValueError in transformers >= 4.46, whereas some Qwen model cards ship generation_config.json files specifying sampling parameters without do_sample: true, causing transformers to silently ignore temperature/top_p/top_k and decode greedily. Always pass do_sample=True explicitly when sampling, or unset sampling parameters when deliberately decoding greedily in non-thinking mode. Fourth, compile your Pydantic v2 8-part output schema into decode-time grammar masks using llama-server's json_schema / GBNF support or XGrammar / XGrammar-2 (integrated into vLLM and SGLang). XGrammar achieves up to 100x mask-generation speedup (and up to 5x time-per-output-token improvement in vLLM according to BentoML's engineering benchmarks), while XGrammar-2 (ACM CAIS '26) introduces TagDispatch—allowing free-form <think>...</think> reasoning followed automatically by grammar-constrained JSON—with over 6x faster compilation and near-zero serving overhead. When serving through llama-server, enable host-memory prefix caching (--cram 256 --system-prompt-file ./fss_system.txt --cache-prompt --cache-type-k q8_0, noting that without --kv-unified, --ctx-size splits across --np slots); a llama.cpp community benchmark (#20574) reported a 93% TTFT reduction (4.3 s down to 0.3 s) for cached prefixes, provided you keep the system prompt byte-identical across queries by never injecting dynamic timestamps or trace_id values ahead of it.

Upgrading Domain Knowledge RAG and Applying Empirical RCA Findings

Vector-only retrieval reliably underperforms on technical failure diagnostics because dense embeddings blur exact alphanumeric identifiers, error codes, and sensor IDs—for example, ranking a generic payment-failure article above the exact runbook for "ERR-482", or conflating "PROD-SKU-7842X" with "PROD-SKU-7842Y". Conversely, lexical search alone misses paraphrases such as matching "stop invoices renewing" against "cancel recurring billing". Upgrading FSS's Domain Knowledge RAG to a lightweight local hybrid retrieval plus reranking pipeline addresses both blind spots without external API dependencies.

For the lexical leg, replace standard pure-Python BM25 (rank-bm25) with bm25s (arXiv:2407.03618), which eagerly precomputes sparse BM25 score matrices in NumPy/SciPy for up to a 500x speedup over rank-bm25, supports exact Lucene, Robertson, BM25+, and BM25L scoring variants, adds under 100KB on disk beyond NumPy/SciPy, and supports memory-mapped indexes that cut RAM usage by over 50% on multi-million-document corpora. One subtle implementation caveat: if JAX is installed in your GPU virtual environment, importing bm25s probes JAX top-k and can trigger GPU VRAM preallocation—set os.environ["XLA_PYTHON_CLIENT_PREALLOCATE"] = "false" prior to importing bm25s. Pair bm25s with a compact local instruction-aware embedding model such as Qwen3-Embedding-0.6B (Apache 2.0, 32K context, configurable MRL dimensions), and merge the lexical and dense rankings using Reciprocal Rank Fusion (RRF):

$$\text{RRF\_score}(d) = \sum_{l \in \{\text{BM25}, \text{Dense}\}} \frac{1}{k + \text{rank}_l(d)}$$

Start with the standard default k = 60 (from Cormack, Clarke, and Büttcher, 2009; also default in Elasticsearch and Milvus, whereas Qdrant defaults to k = 2), which promotes passages appearing near the top of both lists rather than letting a single-list outlier dominate. Re-score the fused top-50 candidate shortlist down to the final top-5–8 passages with a local cross-encoder reranker—noting that a reranker only helps when target passages already appear in the candidate pool, so verify candidate recall first. Closing the Abstention Gap With Pre-Generation Sufficiency Gating

Peer-reviewed evidence from Sufficient Context (ICLR 2025) and recent experimental findings from RINSE: Relevance Is Not Sufficient Evidence (preprint arXiv:2609.37469, September 2026) demonstrate that language models consistently fail to abstain reliably when retrieved evidence is insufficient—even when explicitly instructed to reply "unanswerable". Rather than flagging missing causal links, generators bridge telemetry gaps using stale parametric knowledge or plausible confabulation.

Two architectural rules follow directly for FSS's Data Gaps Quarantine stage. First, enforce a deterministic short-circuit ahead of neural scoring: whenever JavaRetriever returns a legitimate 0-event envelope (status == "EMPTY") or detects unrecorded time gaps spanning the requested failure window, bypass LLM synthesis immediately—or trigger an explicit scope-widening retry akin to RCACopilot's scope-switching handler action—and render a structured INSUFFICIENT_EVIDENCE quarantine card rather than letting the generator improvise. Second, when events are present, insert a lightweight pre-generation sufficiency scorer modeled on RINSE's three complementary checks (question content coverage, RoBERTa-base candidate span detection, and cross-passage latent sufficiency with a ≤1.5B model; 36.5 ms median GPU latency and 0.813 Pairwise Accuracy on real BM25 + e5-base-v2 retrieval outputs). As formalized in TRUST-ALIGN (ICLR 2025), separating sufficiency detection from generation prevents the classic prompt-tuning trap visible across every Qwen3 size—simultaneously over-answering 40.7%–64.3% of unanswerable prompts while falsely refusing 11.3%–29.7% of answerable ones.

Defeating Citation Laundering With Four-Tier Verification and Evidence-Force Calibration

Commit 4a4f568 expanded your citation validator to catch fabricated or malformed tags such as [ev-fake] and [drone-298]. Under the OWASP AI Security Verification Standard (AISVS C07-04) and ForceBench (Findings of EMNLP 2026), syntactic ID validation forms Tier 1 only. Even when every cited ID legitimately exists in the Java BlockStore retrieval set and matches the query topic, LLMs routinely commit citation laundering: citing a real, topically relevant record as warrant for an over-strong claim. In root-cause synthesis, the sharpest failure mode is Relation escalation—citing two temporally proximate [OBSERVED] events and asserting "Event A caused Failure B" without causal support.

To elevate FSS Validation Badges from regex checks to full epistemic auditing, implement a four-tier verification pipeline grounded in OWASP AISVS C07-04, ALCE/ALiiCE, ForceBench, and empirical citation-paradigm evaluations.

Tier 1 — Metadata-Derived ID Integrity and Entity Binding (Deterministic, <5 ms): Verify that every bracketed citation resolves strictly to an event or runbook ID emitted by JavaRetriever or the hybrid RAG layer rather than parametric memory, enforce mandatory paragraph-level citation coverage per AISVS Requirement 7.4.2, and execute a deterministic entity-binding check verifying that the subsystem, host, or sensor named in each claim matches the primary entity in the cited record—catching "deceptive grounding" where valid telemetry from Component Y is misattributed to queried Component X.

Tier 2 — Post-Hoc Attribution Refinement (P-Cite and VeriCite): Comparative evaluation across ALCE and LongBench-Cite (arXiv:2509.21557) found that Post-hoc citation (P-Cite) achieves substantially higher coverage and accuracy on multi-source synthesis than generation-time citation (G-Cite)—reaching 75% coverage and 42% correctness on ALCE versus 37% coverage and 21% correctness for G-Cite, alongside higher human-evaluated answer correctness (78% vs. 69%) and lower citation hallucination (37% vs. 41%). (G-Cite excelled only on single-claim precision in FEVER at 94% correctness with 27% coverage, whereas P-Cite maintained balanced 74% coverage and 75% correctness.) Adopting the three-stage VeriCite flow referenced in OWASP AISVS Requirement 7.4.3—initial synthesis, claim-level evidence verification and selection, and bounded refinement (or abstention after failed retries)—combines broad coverage with strict attribution enforcement.

Tier 3 — Atomic Claim Entailment With Calibration Caveats: Decompose synthesis findings into atomic claims (following FActScore and ALiiCE) and check each claim against its cited records with a compact local verifier—such as MiniCheck-Flan-T5-Large (770M parameters), HHEM-2.1-Open (110M parameters), or a HaluGate-style token-detector plus NLI cascade (76–162 ms). Important counter-evidence caveat: Both FaithJudge (EMNLP 2025 Industry) and a 2026 vendor evaluation by Blue Guardrails on medical RAG documents reported significant limitations in standalone NLI detectors—with Blue Guardrails measuring just 53.6%–62.3% message-level accuracy and 22%–24% claim-level F1 across MiniCheck, Vectara, RAGAS, and cloud guardrails because SNLI-trained models exploit surface negation cues and naive sentence splitting destroys cross-sentence context. Keep surrounding sentence context intact when evaluating claims, treat Tier 3 as a triage signal rather than an infallible oracle, and follow production evaluation guidance (such as FutureAGI's hallucination playbook) by never allowing the generator model to judge its own output, as same-family judging systematically under-reports subtle date, numeric, and citation errors.
